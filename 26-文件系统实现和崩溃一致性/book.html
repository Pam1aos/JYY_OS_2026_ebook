1. 块设备不是一块简单的字节数组

1.1 GPT 分区表

(参考时间: 00:03)

一块磁盘常被划分为多个分区：

/dev/nvme0n1
  /dev/nvme0n1p1
  /dev/nvme0n1p2

分区信息由 GPT 描述：

  • GUID Partition Table；
  • UEFI 规范的一部分；
  • 固件启动时需要解析；
  • 头部记录分区位置、大小和类型；
  • 尾部通常保存备份副本。

    DISK["Block Device"] --> MBR["Protective MBR"]

    GPT --> E2["Partition Entry 2"]
    E1 --> P1["/dev/nvme0n1p1"]
    E2 --> P2["/dev/nvme0n1p2"]

2. 块访问的代价：缓存与读写放大

2.1 更新一个字节可能写多个块

(参考时间: 00:12)

追加一个 4 KB 数据块至少涉及：

  1. 更新数据块 bitmap；
  2. 写入数据块；
  3. 更新 inode 的大小、时间和索引。

如果只修改一个字节：

bread(block)
modify byte
bwrite(block)
update metadata

还会触发 SSD FTL 的映射表更新，导致更严重的读放大和写放大。

flowchart TD
    A["Write 1 Byte"] --> B["Read Whole Block"]
    B --> C["Modify Byte"]
    C --> D["Write Whole Block"]
    D --> E["Update Metadata"]
    E --> F["FTL Mapping Update"]
    F --> G["Read / Write Amplification"]

📷 块级接口会把小修改放大为多块读写
回到原视频 (00:13:30)

2.2 Buffer Cache

(参考时间: 00:15)

操作系统在内存中缓存文件系统块：

  • bread 先查缓存；
  • 命中则直接返回；
  • 未命中才访问块设备；
  • bwrite 先写缓存，之后异步回写。

这与内存层次和共享内存非常相似：

load  ≈ bread
store ≈ bwrite

flowchart LR
    A["bread"] --> B{"Cache Hit？"}
    B -- "是" --> C["Return Cached Block"]
    B -- "否" --> D["Read Device"]
    D --> E["Insert into Cache"]
    E --> C
    F["bwrite"] --> G["Update Cache"]
    G --> H["Write Back Later"]

📷 文件系统通过缓存吸收部分块设备延迟

5. FAT：为极小空间设计的文件系统

5.1 FAT 与 Cluster

(参考时间: 00:26)

FAT 最早面向容量极小的软盘。

物理扇区可能是 512 B，但文件系统把 2^k 个扇区组成一个 cluster：

cluster size = 512 B × 2^k

FAT 的核心是 cluster 的 next 数组。

flowchart LR
    C1["Cluster 1"] --> C2["Cluster 3"]
    C2 --> C3["Cluster 4"]
    C3 --> C4["EOF"]
    FREE["0 = Free"] --> C5["Available Cluster"]

📷 FAT 把文件组织成 cluster 链表
回到原视频 (00:26:30)

5.2 FAT 表就是 next 数组

(参考时间: 00:29)

FAT-12 使用 12 位指针：

0      = free
EOF    = cluster chain end
other  = next cluster

12 位不是字节整数，因此两个 FAT-12 entry 会打包进 3 个字节：

24 bits = entry[i] (12 bits) + entry[i+1] (12 bits)

flowchart TD
    A["FAT Entry 1: 12 bits"] --> C["3-byte Packed Block"]
    B["FAT Entry 2: 12 bits"] --> C
    C --> D["Next FAT Entry"]

📷 FAT-12 按 bit 压紧存储，极限节省空间
回到原视频 (00:29:30)

5.3 FAT 碎片

(参考时间: 00:32)

频繁分配和释放会产生碎片：

file clusters:
  464 → 465 → 466 ... 546

another file:
  2407 ... 2431 → 2511 ... 2587

大文件碎片化后：

  • cluster 链跳跃；
  • FAT entry 本身也可能跨块；
  • lseek 随机访问需要反复跟踪链；
  • 产生严重读放大。
flowchart LR
    A["Logical File Blocks"] --> B["FAT Linked Clusters"]
    B --> C1["Contiguous Run"]
    B --> C2["Jump to Far Cluster"]
    C2 --> C3["Jump Back"]
    C3 --> D["Seek / I/O Amplification"]

📷 碎片化让 FAT 链式索引产生大量随机 I/O

7. 崩溃一致性：块写入不是事务

7.1 一次 append 涉及多次写

(参考时间: 00:51)

追加一个数据块：

1. bwrite(block bitmap)
2. bwrite(data)
3. bwrite(inode)

每个操作本身可能成功，但设备可以重排写顺序。

flowchart LR
    A["Allocate Block"] --> B["Update Bitmap"]
    B --> C["Write Data"]
    C --> D["Update Inode"]
    D --> E["Filesystem Visible"]
    F["Crash at Any Point"] --> G["Possible Inconsistent State"]

📷 追加一个块涉及 bitmap、数据和 inode 三处更新

7.2 设备会重排写入

(参考时间: 00:55)

从文件系统到物理介质之间有多层队列：

block cache
  → block queue
  → HDD scheduler / SSD FTL
  → flash controller

HDD 会优先选择距离读写头最近的请求；SSD 会把写分配到不同物理块。

flowchart TD
    A["bwrite 1"] --> Q["Device Queue"]
    B["bwrite 2"] --> Q
    C["bwrite 3"] --> Q
    Q --> D["Reordered Physical Writes"]
    D --> E["Crash May Persist Any Subset"]

📷 设备队列可能重排写请求，崩溃时只保留任意子集
回到原视频 (00:56:00)

7.3 2³ 种结果

(参考时间: 00:56)

三个块写入在崩溃后可形成 2³ = 8 种已落盘子集。

例如：

inode 已更新
data 已更新
bitmap 未更新

文件当前看起来正常，但未来 bitmap 会再次分配该块，导致数据被覆盖。

flowchart TD
    A["Inode Points to Block 40"] --> B["Block 40 Contains Hello"]
    C["Bitmap Still Marks Block 40 Free"] --> D["Future Allocation Reuses Block 40"]
    D --> E["File Data Corrupted Later"]

📷 bitmap 与 inode 不一致会在未来导致静默数据损坏

9.2 LSM Tree

(参考时间: 01:06)

Log-Structured Merge Tree：

  • 内存 MemTable 负责写；
  • WAL 保证崩溃恢复；
  • MemTable 满后 Flush；
  • 磁盘只保存 immutable SSTable；
  • 定期 Merge 小树到大树。
flowchart TD
    A["Write Request"] --> B["MemTable"]
    A --> C["WAL"]
    B --> D{"MemTable Full？"}
    D -- "是" --> E["Flush to SSTable"]
    E --> F["Merge Lower Levels"]
    C --> G["Crash Recovery"]

📷 LSM 把写集中到内存并使用 WAL 保证恢复
回到原视频 (01:06:30)

9.3 Write-ahead Log

(参考时间: 01:08)

文件系统日志：

  1. 写 TXBegin；
  2. 写实际要修改的块；
  3. flush；
  4. 写 TXEnd；
  5. flush；
  6. 后台 checkpoint 到真实位置；
  7. 回收日志。
flowchart TD
    A["TXBegin"] --> B["Journal Operations"]
    B --> C["flush"]
    C --> D["TXEnd"]
    D --> E["flush"]
    E --> F["Replay / Checkpoint"]
    F --> G["Reclaim Journal"]

📷 日志用 flush 建立 TXEnd 与数据落盘的 happens-before 关系
回到原视频 (01:08:30)

9.4 Checkpointing

(参考时间: 01:10)

如果崩溃发生在 TXEnd 之前：

事务视为未完成

如果崩溃发生在 TXEnd 之后：

事务可完整 replay

flowchart TD
    A["Crash Before TXEnd"] --> B["Ignore Transaction"]
    C["Crash After TXEnd"] --> D["Replay Transaction"]
    D --> E["Filesystem Updated"]

📷 TXEnd 决定日志事务是否在恢复时重放

9.5 批处理与 JBD

xv6、JBD 等实现会：

  • 合并多个系统调用；
  • 延迟回写；
  • 减少 flush 次数；

9.6 ext4 checksum

(参考时间: 01:12)

ext4 可以：

  • 不再依赖传统 TXBegin/TXEnd 标记；
  • 在日志头记录长度和 checksum；
  • 恢复时验证 checksum；
  • checksum 错误则丢弃整个尾部事务。
flowchart TD
    A["Journal Header"] --> B["Length + Checksum"]
    B --> C["Replay / Scan"]
    C --> D{"Checksum Valid？"}

9.7 Metadata Journaling

(参考时间: 01:14)

ext4 默认元数据日志：

  • inode、bitmap、目录结构进日志；
  • 文件数据不进日志；
  • 保证目录树一致；
  • crash 可能丢最近数据。

10. 应用程序也必须实现崩溃一致性

10.1 常见的错误保存方式

(参考时间: 01:15)

看起来合理的文件保存：

Path("a.txt.tmp").write_text(new_data)
unlink("a.txt")
rename("a.txt.tmp", "a.txt")

但元数据日志可能只重放了：

create a.txt.tmp
unlink a.txt

而没有重放数据写入，最终用户看到文件消失。

sequenceDiagram
    participant App
    participant FS
    App->>FS: create temp
    App->>FS: write temp
    App->>FS: unlink original
    App->>FS: rename temp
    Note over FS: Crash before data durable
    FS-->>App: Replay metadata only
    App->>FS: File missing / empty

📷 临时文件、删除和重命名如果没有同步点，崩溃后可能丢文件
回到原视频 (01:15:30)

10.2 Git 的 crash consistency

(参考时间: 01:17)

Git 是 append-only object store，通常不调用同步：

  • 对象一旦写入，不像普通文件那样原地修改；
  • FSCK 可以恢复引用图；
  • 快速关闭虚拟机可能导致 Git 目录不一致；
  • git fsck 可以重新扫描对象。

课程 makefile 中加入全局 sync 以保证提交落盘。

flowchart TD
    A["Git Objects"] --> B["Append-only Store"]
    B --> C["Crash May Leave Partial Filesystem"]
    C --> D["git fsck"]
    D --> E["Recover Object Graph"]

📷 Git 靠 append-only 对象图和 fsck 恢复崩溃后的状态
回到原视频 (01:17:30)

10.3 sync 系列系统调用

(参考时间: 01:19)

sync();
syncfs(fd);
fsync(fd);
fdatasync(fd);

区别：

调用 同步范围
sync 所有文件系统
syncfs 一个文件系统
fsync 文件数据 + 全部元数据
fdatasync 文件数据 + 影响读回的必要元数据 
flowchart LR
    A["sync()"] --> B["Global"]
    C["syncfs(fd)"] --> D["Filesystem"]
    E["fsync(fd)"] --> F["File + Metadata"]
    G["fdatasync(fd)"] --> H["File Data + Minimal Metadata"]

📷 不同 sync 调用覆盖的持久化范围不同

10.4 fdatasync 与数据库

(参考时间: 01:21)

固定大小的数据库文件：

  • 空间早已分配；
  • 修改数据不改文件大小；
  • inode block map 不变；
  • fdatasync 不需要同步大多数 inode 变化。

因此数据库 WAL 常优先使用 fdatasync。

flowchart TD
    A["Fixed-size Database File"] --> B["Data Written"]
    B --> C["Size Unchanged"]
    B --> D["Block Map Unchanged"]
    C --> E["fdatasync"]
    D --> E
    E --> F["Avoid Inode Write"]

📷 fdatasync 适合固定大小数据库和自定义 WAL

10.5 正确保存文件

(参考时间: 01:22)

基本模式：

关键要求：

  • 新数据先 fsync；
  • rename 由文件系统提供原子性；
  • 必要时再同步目录项。

12. 总结：用合适的数据结构守护持久数据

文件系统实现包含多个层次：

  1. 用 GPT、LVM、NVMe Namespace 等虚拟化块设备；
  2. 用 Superblock 建立入口；
  3. 用 FAT 或 inode 组织文件块；
  4. 用目录项组织命名图；
  5. 用缓存降低块访问成本；
  6. 用 FSCK 修复非一致状态；
  7. 用 WAL/Journal 保证多块更新原子性；
  8. 用 fsync、fdatasync 和原子 rename 保证应用级持久性。
flowchart TD
    A["Block Device"] --> B["Partitions / LVM"]
    B --> C["Superblock"]
    C --> D["Allocation Metadata"]
    C --> E["Inodes"]
    C --> F["Data Blocks"]
    E --> G["Directory Graph"]
    G --> H["Filesystem Operations"]
    H --> I["Journal / WAL"]
    I --> J["Crash Consistency"]

核心结论：

文件系统不是必须照搬教科书的固定结构，而是围绕硬件、workload 和一致性要求设计的数据结构。持久数据的安全来自底层日志、同步协议和应用程序保存协议的共同配合。
